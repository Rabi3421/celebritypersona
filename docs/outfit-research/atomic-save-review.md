This report supersedes the ordinary-save compatibility conclusions in the earlier final review. Work is local and uncommitted on `feat/outfit-research-import`. ## Root cause and writer audit

The old ordinary create/edit functions persisted the outfit first, then created missing celebrity, occasion and brand records with independent writes. A subsequent unique-name or numeric-ID failure therefore left the outfit committed while the action reported failure. Related records inserted earlier could also remain. Numeric `max(id)+1` allocation outside a serialized transaction raced. Hub renames could persist URL redirects before their record/reference updates succeeded. Snapshot transactions alone would still allow two different drafts to publish the same primary keyword (write skew).

| Writer | Previous atomicity | Corrective behavior |
| --- | --- | --- |
| Ordinary outfit create, edit, draft and publication via admin action | Outfit write atomic individually; related writes separate | One shared serialized transaction; version check for edits; stable request identity for creates |
| Imported draft creation | Transactional, separate backend | Same backend; import-only validation, approvals, source identity and draft restriction retained |
| Celebrity/occasion create, edit, explicit rename/merge | Separate hub, reference and redirect operations | Same serialized transaction; duplicate create/edit errors; deletion only during explicit merge or delete |
| Outfit and celebrity/occasion deletion | Single delete; no shared order | Database delete participates in coordination; image cleanup/revalidation follow commit |
| Brand intro/SEO editing | Single-document update | Remains single-document atomic; validated input excludes name and numeric ID |
| `backfill-records.ts` | Separate batch inserts and stale max-ID allocation | One transaction, fresh published-outfit snapshot, shared identity resolution and ID allocator |
| `set-outfit-status.ts` | Raw status update bypassing publish checks | Shared outfit persistence, source fingerprint, related records and publication checks |
| `freeze-slugs.ts`, `backfill-seo.ts`, `retag-occasions.ts` | Independent updates from an earlier plan | Whole plan transactional with complete source fingerprint checks; retag also ensures related records |
| `migrate-links.ts`, `check-links.ts`, `strip-seed-outfit.ts` | Raw item-array updates could overwrite newer edits | Whole plan transactional with source checks; external link lookups and backups remain outside retry callbacks |
| `purge-seed-content.ts` | Deletes/bio clear could partially succeed | Whole operation transactional; source fingerprints checked; delete IDs restricted to inspected documents |

`seed-content.ts` writes `siteContent`, not catalog records; `seed-admin.mjs` writes users; Instagram mirroring writes site content. Other actions write mail, subscribers, clicks, reports, requests, budget pages and home content, not the indexed identity fields. SEO research uses its existing separate revision-checked `seoReviews` store; previews do not create catalog records. No production maintenance script was executed. Direct MongoDB tools, old deployed binaries and external writers remain outside these guarantees and must be excluded during rollout.

## Implementation and boundaries

New shared modules are `lib/archive-name.ts` and `lib/db/catalog-{errors,indexes,transaction,identity,redirects,outfits,hubs,maintenance}.ts`. `imported-outfits.ts` is now a compatibility adapter. `mutations.ts`, admin outfit/new/edit pages, outfit actions/form fields/form, celebrity/occasion actions and the listed maintenance scripts call those primitives. Test additions live in `tests/catalog-outfits-db.test.mjs`; existing import database/browser fixtures now provision the local coordination document. The original import feature/security/dependency changes remain part of the larger uncommitted feature diff.

Every dependent database operation uses the same session, sequentially. The transaction starts by incrementing one operator-provisioned document in `catalogWriteState`: `{_id:"catalog", version:0}` initially. This establishes a serial order **before** reading IDs, outfits, identity records or publication keyword ownership. The operation then resolves identities, checks current state, writes hubs, outfit and any URL redirects, and commits with primary reads, snapshot read concern and majority write concern. Failed operations roll back the coordination increment too. The document is a coordination mechanism, not an outfit revision or counter allocation schema.

This is one necessary additive collection/document beyond the six unchanged index definitions. It is **not provisioned automatically**, has only MongoDB's native unique `_id_` index, and needs separate rollout approval. Missing coordination or required indexes fails before any content writes. Ordinary catalog transactions require the three existing ID indexes plus the five proposed non-import indexes; imports additionally require the proposed post-identity index. Sparse or incompatible partial/collation indexes are rejected. A compatible stronger full slug/post index is accepted.

`nextCatalogId` checks all existing IDs for positive safe integers and allocates max+1 inside the serialized transaction, capped at 999,999,999. This applies to brands, outfits and hubs. Numeric unique indexes remain the final defense against a nonparticipating writer; such a collision fails the whole transaction and never becomes reuse. Deleted highest IDs can be allocated again, matching the old max+1 model; this is not a permanent monotonic sequence.

Names use NFC, trimmed/collapsed whitespace and lowercase comparison. Stored spelling is retained when genuinely matched. Accents, punctuation and aliases are not stripped. Multiple legacy normalized matches are refused. A database collation match without a genuine application identity match is refused. Unrelated duplicate keys are never converted into successful saves. Explicit hub create/edit cannot silently merge; merging remains an explicit operation.

The driver can retry transient transaction conflicts within an 8-second transaction deadline (5-second maximum commit time). There is no generic duplicate-key retry loop. Retry callbacks contain database operations only. Create requests carry a stable UUID from the browser's autosaved draft; actor+UUID maps to a deterministic native `_id`. Concurrent/replayed requests return the original outfit and never apply a changed body. Imported `_id` remains deterministic from the canonical Instagram post URL. Preflight checks do not prevent ordinary-create replay. On an uncertain create response, preserve the same browser draft/request identity; inspect the list before starting a new form.

Edits submit a server-generated SHA-256 fingerprint of the complete originally loaded outfit, excluding native `_id`; no revision backfill is needed. A mismatch rejects the transaction and preserves submitted values. Successful edits that remain on the form receive the new fingerprint. Autosave retains the original fingerprint/token; restoring an old draft cannot silently adopt the current record's version. Old forms without a fingerprint/token must reload and preserve their text first.

Publication requirements, lead piece, locked slugs and effective-slug uniqueness are rechecked inside the transaction. Different-draft publication is serialized against current keyword ownership. First-publication stamps commit with the outfit; failed publication creates no stamps. Existing live legacy looks retain their established ability to save with SEO warnings. Existing research/unknown metadata are retained on edits; legacy image fields are removed only with the existing migration to the submitted photo array.

Firebase deletion, public revalidation and IndexNow occur **after confirmed commit**, once per non-replayed call, outside driver retries. Failed persistence does not run them. A post-commit refresh failure is reported as saved with refresh unconfirmed, never as an unsaved database operation. External effects are not durable/transactional: a process crash after commit can leave cleanup/revalidation pending; no outbox or exactly-once external delivery is claimed. Existing standalone hub post-commit refresh behavior remains unchanged.

## Migration reassessment and approvals

All six proposed indexes remain necessary and unchanged; see the revised `index-migration-plan.md` for per-index null/empty/legacy assessment, verification and rollback. This local implementation removes the previously demonstrated partial-save failure under those constraints. It does **not** certify current production data: the earlier read-only inventory must be repeated immediately before any migration.

Recommended sequence: separately review/approve this source and dependency decisions; separately approve the six indexes **and coordination collection/document/permissions**; pause all catalog writers and drain in-flight requests/jobs; take a managed backup and repeat compatibility audits; create only missing approved indexes and the coordination document using an operator role; verify unchanged content; deploy the reviewed compatible backend with imports disabled; verify normal admin behavior using an approved isolated test plan; reopen ordinary writes; separately approve a real import pilot and enablement. Old server instances and stale maintenance processes must not remain writable alongside the new implementation.

During rollback, first keep/turn imports off and pause/drain catalog writes. Prefer retaining this transactional backend and its compatible indexes with imports disabled. Do not restore the known nontransactional writer while the new constraints remain: it recreates the blocker. Binary rollback requires a separately approved version with these ordinary-save protections and security patches, or a paused-write corrective plan. Dropping only migration-created indexes needs separate approval and the creation ledger. Never automatically remove hub/outfit data, provenance or coordination while transactions may still run. An 8-second app deadline is not proof that all server transactions have drained: an operator must inspect sessions/transactions and resolve uncertain outcomes before DDL or binary rollback.
